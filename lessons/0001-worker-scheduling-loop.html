1. 你实际使用的产品是什么

普通用户主要打开 Element Web。它是 Matrix 聊天系统的网页客户端：你可以在 Manager 的私聊里要求创建团队成员，也可以进入某个 Worker 的房间直接布置任务、追问进度和人工纠正。正常完成任务时，你不需要运行 agt。

角色使用入口在系统里做什么
普通用户Element Web / 其他 Matrix 客户端用自然语言创建团队、分配任务、看进度和结果
Manager AgentMatrix 消息 + 内置技能理解需求、拆任务，并间接调用管理命令创建或唤醒 Worker
运维人员安装脚本、Docker、Helm、agt部署平台、管理资源、检查状态和自动化操作
Worker Agent自己的 Matrix 房间和工作区接收任务、操作代码和工具、汇报过程与结果

2. 运维怎样把它部署出来

本机体验：Docker Compose

克隆仓库后设置模型密钥并运行 make install。安装结果至少包含 agentteams-controller 和 agentteams-manager 两个主要容器；前者还承载本地版的聊天、模型网关、对象存储和网页入口。Worker 是用户创建后才出现的 agentteams-worker-* 容器。

用户随后打开 http://127.0.0.1:18088 登录 Element Web。

生产部署：Kubernetes + Helm

Helm 安装 Matrix、Higress、对象存储和 Controller。Controller 监听 Worker、Manager、Team、Human 等配置记录，并把 Worker 落成 Pod。生产环境不是把所有程序塞进 Manager 容器。

操作入口：docs/zh-cn/quickstart.md → install/agentteams-install.sh → helm/agentteams/

3. agt 到底是什么，为什么还需要命令行

agt 是 AgentTeams 资源管理命令行，可以把它类比成这个平台自己的精简版 kubectl。它把 create worker、get workers、wake、sleep 等确定性操作转换成 Controller 的 HTTP 请求。它本身既不聊天，也不运行模型，更不直接等于一个 Worker。

保留 CLI 有三个原因：运维可以手工检查和脚本化管理；Manager 可以通过技能调用同一套稳定接口，而不用让模型拼接 Docker 命令；Worker 可以用少量生命周期命令报告就绪状态。本地安装把它放进 Controller 和 Manager 容器，因此运维可以执行：

docker exec agentteams-controller agt create worker --name alice --model qwen3.5-plus
docker exec agentteams-controller agt get workers
不要混淆两条入口：“请帮我创建 Alice”是普通用户发给 Manager 的自然语言；agt create worker ... 是 Manager 技能或运维脚本最终调用的精确管理操作。两者会走到同一个 Controller API。

源码入口：agentteams-controller/cmd/agt/main.go

4. 一个常见用户故事，从部署到交付

  1. 运维先装平台。Controller、Manager、Matrix、Higress 和对象存储上线；此时不要求每个未来成员都已有容器。
  2. 用户在 Element 中找 Manager。例如发送：“创建一个叫 Alice 的前端 Worker，使用指定模型和 GitHub 技能。”
  3. Manager 把自然语言变成资源操作。它通过内置技能调用 agt；Controller 保存 Alice 的期望配置，准备聊天身份、模型权限、存储目录和 Worker 容器。
  4. 用户进入 Alice 的 Matrix 房间发任务。例如“修改登录页并运行测试”。Manager 也可以先把任务说明和元数据写入 shared/tasks/<task-id>，再通知 Alice。
  5. Alice 在自己的容器中执行。她从对象存储取得工作区和技能，经 Higress 调模型或 MCP 工具；进度、提问和人工干预都出现在聊天室。
  6. 结果分两路回来。代码和大文件写回对象存储，完成摘要和状态发回 Matrix。容器以后即使重建，持久文件仍可恢复。

如果用户只想从终端复现一次任务，仓库也提供 make replay TASK="..."；它是测试和自动化入口，不改变“聊天室是主要人机协作界面”的产品设计。

5. 先改掉“Manager 直接启动 Worker”的直觉

AgentTeams 把“需要什么 Agent”和“怎样启动容器”拆开。Manager 可以调用管理命令 agt，但它只提交一条希望系统达到的状态，例如“需要一个叫 Alice、当前应在线的 Worker”。这条 Kubernetes 自定义记录叫 Worker 配置记录（Worker CR）。

真正创建容器的是持续检查程序（Controller）。它反复执行对齐检查（Reconcile）：比较“希望状态”和“真实状态”，然后补上差距。

Manager表达意图
管理 API写 Worker 配置
持续检查程序发现并补齐差距
运行环境驱动建容器 / Pod
Agent 运行程序等待并执行任务

配置记录里的 spec 保存希望状态，status 保存系统观察到的状态。即使底层使用 Docker，上层仍按这个循环工作。若底层换成 Kubernetes，Pod 可以先理解成“由 Kubernetes 管理的容器运行单元”。

6. 沿源码走完七步

  1. CLI 构造请求。 createWorkerCmd 收集名称、模型、runtime、skills 等字段，POST 到 /api/v1/workers，随后轮询 Ready。 cmd/agt/create.go
  2. HTTP 接口创建 Worker 配置记录。 接口先保存“想要什么”，不在这次 HTTP 请求里完成所有启动步骤。 internal/server/http.go
  3. Worker 对齐检查程序被唤醒。 它读取配置和当前状态；删除保护标记、状态更新等 Kubernetes 细节都在这里处理。 internal/controller/worker_controller.go
  4. 身份准备服务（源码名 Provisioner）建立 Agent 身份。 它创建Matrix 聊天用户和房间、模型网关访问身份，以及对象存储账号和权限。 internal/service/provisioner.go
  5. 工作区生成服务（源码名 Deployer）写入配置。 它把模型、聊天登录凭证、角色说明、技能和工具配置写入 agents/<name>。 internal/service/deployer.go
  6. 运行环境驱动（Backend）创建运行载体。 同一份创建请求可以翻译成 Docker 容器请求或 Kubernetes Pod 请求。 internal/backend/interface.go
  7. Agent 运行程序（Runtime）恢复状态并上线。 容器启动脚本从对象存储拉取工作区，连接聊天房间，启动等待任务的循环，最后报告“已经就绪”。 worker/scripts/worker-entrypoint.sh

7. 通信不是一条通道，而是两条

Matrix 聊天室：协调通道

Matrix 是一种开放聊天协议。任务指派、问题、进度、人工干预和完成通知都作为房间消息出现，让 Human、Manager 和 Worker 看到同一条时间线。

对象存储（MinIO / OSS）：数据通道

对象存储是可通过网络访问的持久文件仓库，适合保存配置、技能、记忆、任务说明、代码工作区和结果文件。容器销毁后，这些文件仍然存在。

关键词：agents/、shared/tasks/、mirror、sync。

因此，“请 Alice 修改一个仓库”通常表现为：Matrix 中发送可见指令；对象存储中出现任务目录和产物；Matrix 中再发送完成或阻塞事件。消息负责协调，文件负责承载工作。

8. 运维怎样沿链路排查故障

先从用户看到的症状反向检查：Element 能否打开并登录 → Manager 是否在线 → agt get workers 中期望状态和实际状态是否一致 → Worker 容器 / Pod 是否存在 → Worker 是否连入 Matrix → 对象存储工作区是否可读。这样能判断问题是在产品入口、调度、运行环境、通信还是文件恢复层。

9. 用一个故障检验心智模型

情景

Worker 的 Docker 容器被意外删除，但 Worker 配置记录仍写着“应该在线（Running）”。

先口头预测，再展开答案

下一轮对齐检查会发现容器缺失，通过运行环境驱动重新创建。新的 Agent 运行程序从对象存储恢复工作区，再连接聊天室。Manager 不需要记住并重放一次 docker run。
