先建立地图
再进入四个仓库

四个项目都能让多个 Agent 协作，但用户看到的产品、运维部署的服务、CLI 的用途和内部调度对象都不同。先从一次完整使用过程建立地图，再进入源码。

前置：了解 Go、Docker 容器 · 不要求了解 Kubernetes 或 Agent 框架术语

课程规则：第一次出现项目术语时先解释中文含义，英文只作为源码搜索关键字。遇到不清楚的词，可以打开名词表。

1. 每个仓库都按同一条端到端路线阅读

  1. 用户到底打开什么？是浏览器聊天室、协作网页，还是现有的 Codex / Claude 命令行界面？
  2. 运维需要部署什么？哪些是中央服务，哪些程序必须装在真正执行代码的机器上？
  3. 仓库为什么还提供 CLI？它是普通用户界面、管理员工具、后台程序入口，还是供 Agent 间接调用的确定性工具？
  4. 完成一个常见任务会经过谁？从用户输入开始，依次指出产品入口、调度者、执行进程、结果回传位置。
  5. 系统长期保存什么？是 Agent 身份、连续会话、运行清单，还是一项项任务？
  6. 谁决定由哪个 Agent 执行？是 Manager 的模型推理、数据库队列、父 Agent，还是操作者？
  7. 真正执行代码的进程怎样启动？长期在线、休眠唤醒、每轮启动，还是领取任务后启动？
  8. Agent 怎样交换结果，失败后又从哪里恢复？区分消息通道、文件通道和持久状态。
课程阅读顺序：每个独立课程都先回答“产品是什么、谁在用、如何部署、CLI 干什么”，再完整走一遍常见用户故事，最后才拆解内部源码。这样后文出现 agt、Daemon、Gateway、Runner 时，你已经知道它们在整套产品中的位置。

3. 不要把四者过早压成一种“调度器”

AgentTeams 主要管理长期 Agent 及其容器；AgentSpace 主要管理等待执行的任务；houmao 主要管理可恢复的单 Agent 会话；omnigent 主要管理按委派扩展的父子会话树。

这些边界可以组合。例如，一个平台可以用 AgentTeams 管理长期身份，用 houmao 保存本机 Agent 会话，用 omnigent 生成临时子 Agent，再用 AgentSpace 的任务队列做可靠执行。是否应该组合，要等学完各自实现后再判断。

4. 推荐学习顺序

  1. AgentTeams：先理解长期 Agent 和容器生命周期。
  2. AgentSpace：再理解任务级的可靠领取。
  3. houmao：学习进程与身份之间如何用运行清单解耦。
  4. omnigent：学习父 Agent 如何动态生成独立子会话。
  5. 综合比较：最后再讨论预热、通信、并发和恢复的取舍。
