omnigent
如何生成父子 Agent 会话树

本课只看 omnigent：一个根 Agent 如何通过工具委派任务，按需创建使用不同执行器的子 Agent，并异步取回结果。

主线：Agent 定义 → 根会话 → Server / Runner → 子会话 → 结果箱

先记住一句话：omnigent 把每个 Agent 运行实例表示成一个独立会话；多个 Agent 就是由父子关系连接起来的一棵会话树。

1. 用户可以从 Web 进入，也可以直接用 CLI

个人本机体验时，运行 omnigent 就能选择模型、创建会话并打开本地 Web UI（默认 http://localhost:6767）；也可以执行 omnigent claude 或 omnigent codex，直接进入原生命令行 Agent。要运行仓库中已经打包好的多 Agent 定义，可以使用 omnigent run examples/polly/。

因此 omnigent CLI 不只是管理员工具。它同时承担首次安装和登录、本地产品启动、直接运行 Agent、连接远程 Server、启动执行主机以及附加已有会话等职责；浏览器则更适合查看会话树、事件和协作状态。

角色 / 程序入口职责
普通用户Web UI 或 omnigent CLI选择 Agent、创建会话、发送任务、查看父子执行树
Server中央 HTTP / 事件服务保存用户、Agent 定义、会话树、事件、文件和权限
Hostomnigent host让一台有代码、工具和凭据的机器上线成为执行主机
RunnerHost 内部执行服务为会话准备目录，启动 Claude、Codex 等 Harness

2. 运维怎样部署：中央 Server 和执行主机分开

单机体验

安装 omnigent 后运行 omnigent server start，再运行 omnigent host。Server 保存状态，Host / Runner 在本机实际启动 Agent。也可以直接运行 omnigent 使用整合的本地流程。

团队或远程部署

运维用仓库 deploy/ 下的 Docker Compose 部署 Server；开发者电脑无需暴露入站端口，只需 omnigent login https://your-host 后运行 omnigent host https://your-host，由 Host 主动连向 Server。

关键部署边界：Server 在线只代表会话和网页可用。要在某台机器的仓库中真正运行 Codex / Claude，那台机器还必须有在线 Host、对应 CLI、凭据和代码目录。

操作入口：omnigent/README.md → omnigent/deploy/README.md

3. 一个常见用户故事

  1. 运维部署 Server，开发者启动 Host。Server 负责公共状态，Host 报告自己可执行哪些 Harness。
  2. 用户在 Web 中选择 Polly 等多 Agent 定义并创建根会话。输入例如“分析这个功能并分别给出实现和测试建议”。
  3. Server 保存根 Session 并路由到在线 Host。Runner 在目标机器准备工作目录，启动根 Agent 的 Harness。
  4. 根 Agent 自己拆分任务。它调用 sys_session_send 委派给允许的 Codex 或 Claude 子 Agent；第一次委派会创建独立子 Session。
  5. 多个子 Session 独立执行。它们可以使用不同 Harness 和上下文，进度事件持续回到 Server，Web 中显示为一棵树。
  6. 结果进入根会话的 Inbox。根 Agent 用 sys_read_inbox 读取各子任务结果，汇总后回复用户；Server 保存整棵树供追踪和恢复。

4. 五个对象先分工

对象普通中文含义主要职责
AgentSpecAgent 定义声明提示词、工具权限、使用哪个执行器、允许调用哪些子 Agent
Session一次连续 Agent 会话保存消息历史、状态、父子关系和这次运行使用的 Agent 定义
Server中央状态服务保存会话树、权限、事件、文件和产物，并把本机工作路由给 Runner
Runner本机执行服务准备工作目录，启动命令行或程序接口 Agent，执行本机工具
HarnessAgent 启动适配器统一 Claude Code、Codex 和其他 Agent 客户端的启动、输入和输出

5. 根 Agent 怎样启动

  1. 用户选择一个 Agent 定义并创建根会话。Server 先保存会话记录、所有者和 Agent 配置。
  2. 会话绑定某个在线 Runner。这决定工作实际落在哪台主机执行。
  3. Runner 准备工作目录和文件。不同会话可以共享项目，也可以使用隔离目录。
  4. Runner 根据 Agent 定义选择 Harness。例如启动 Claude Code、Codex，或直接通过程序接口调用模型。
  5. 第一条消息进入会话事件流。Harness 开始推理并决定是否调用工具或创建子 Agent。

源码入口：server/routes/sessions.py → host/connect.py → runner/app.py

6. 原生命令行 Agent 和程序接口 Agent 接工具的方式不同

程序接口 Agent

Runner 自己构造模型请求，因此可以直接把工具说明放进请求，并在收到工具调用后执行。

Claude Code / Codex 等原生客户端

Runner 不能随意改写它们内部的每次模型请求，所以通过启动配置、终端桥接、技能和工具连接协议（MCP）提供平台工具。

不同 Harness 不需要理解彼此内部协议。它们只需要在各自一侧理解 omnigent 提供的会话事件和工具接口。

7. 第一次委派时按需创建子会话

父 Agent 调用 sys_session_send，表达“把这项工作交给名为 codex 的逻辑子 Agent”。这个工具不是简单地向某个进程写字符串，而是完整的子 Agent 调度入口。

父 Harness 调用 sys_session_send(agent="codex")
Runner 检查父 Agent 是否允许调用这个子 Agent
查找是否已有同名、同标题的直接子会话
没有则请求 Server 创建，并写入父会话编号和同一 Runner
根据子 Agent 定义启动 Codex Harness 并投递第一条消息

后续向同一子任务发送消息时，系统复用已有子会话，保留上下文。父 Agent 也可以直接使用子会话编号继续对话，但只能控制自己的直接子节点。

源码入口：tools/builtins/spawn.py → runner/tool_dispatch.py → server/routes/sessions.py

8. 子任务异步执行，结果回到父会话结果箱

sys_session_send 不等待子 Agent 完成，而是立即返回一个异步任务标识。子 Agent 在自己的会话中独立工作，拥有自己的上下文、历史和执行进程。

完成、失败或取消后，Runner 把结果写入父会话的结果箱（Inbox）。父 Agent 调用 sys_read_inbox 读取结果，再继续推理和汇总。

父 Agent委派
子 Session独立执行
Inbox保存完成结果
父 Agent读取并汇总

9. 为什么它是一棵树，而不是任意 Agent 互发消息

每个子会话保存 parent_session_id 和根会话编号。父 Agent 默认只能创建、继续、查看或停止自己的直接子会话。这条边界让 Server 能检查权限、统计成本、显示运行树，也避免任意会话跨用户控制。

如果某个子 Agent 的定义也允许调用子 Agent，它可以继续创建下一层，于是形成多层树。递归能力来自配置授权，不是所有 Agent 自动拥有。

10. 同一会话串行，不同子会话可以并行

同一 Session 同时只处理一轮正在执行的输入，新消息按顺序处理或安全注入。多个 Child Session 是不同执行单元，所以可以并行使用不同 Harness。

Server 持久保存会话和事件，Runner 管理实际进程。Runner 断开时会话记录不会消失；重新绑定可用执行主机后，可以根据会话状态重新启动 Harness。

11. 运维怎样端到端排查

按这条链检查：Server 健康、数据库和登录是否正常 → Web 中是否有在线 Host → 目标 Session 绑定了哪个 Runner → 那台机器是否安装对应 Harness CLI 和凭据 → 根会话是否产生子会话 → 子会话事件是否结束 → 结果是否写入父会话 Inbox。网页能打开并不等于执行主机已经就绪。
