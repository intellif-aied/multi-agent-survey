AgentSpace
如何可靠执行一项任务

本课只看 AgentSpace：一条频道消息或任务请求，如何变成数据库队列项，再被本机服务领取并交给 Codex、Claude 等命令行 Agent。

主线：任务服务 → 数据库队列 → 常驻执行服务 → 执行器路由 → 完成写回

先记住一句话：AgentSpace 长期保存的是“任务及其执行记录”，不是为每个逻辑员工长期保留一个 Agent 进程。

1. 用户打开什么，CLI 又是谁用的

AgentSpace 对普通用户呈现的是一个浏览器协作空间，默认本机地址是 http://127.0.0.1:1455。用户在网页里建立工作区和频道、配置数字员工、发布消息或任务、查看执行过程，并审批敏感操作。

agent-space CLI 主要面向运维、开发者和自动化脚本。它负责初始化数据库、启动后台执行服务、创建或检查工作区资源，以及执行 doctor、daemon status、task list 等诊断命令。普通成员日常协作不需要先学会这些命令。

角色入口职责
普通用户Web 中的频道、任务、审批提出工作、查看过程、批准或拒绝高风险动作
逻辑员工数据库中的 Employee 记录表示职责、权限和任务归属，不是常驻进程
Daemon部署在执行机器上的常驻后台程序领取任务并启动本机 Codex、Claude 等工具
运维人员Docker Compose + CLI维护 Web、PostgreSQL、Daemon、凭据和执行器

2. 运维怎样部署完整执行链

  1. 准备 Node.js 和 PostgreSQL。仓库提供的 Compose 可以先启动 PostgreSQL。
  2. 安装依赖并初始化数据库。依次运行 npm run setup、复制环境配置，再执行 npm run db:pg:init。
  3. 启动 Web 服务。npm run dev:web 提供浏览器产品入口。
  4. 在真正执行任务的机器启动 Daemon。这台机器还要安装对应的 Codex、Claude 等命令行程序及凭据。Daemon 可以和 Web 同机，也可以带令牌连接远程 Server。
docker compose -f deploy/postgres/docker-compose.yml up -d
npm run db:pg:init
npm run dev:web
npm run cli -- daemon start

操作入口：AgentSpace/README.md → apps/cli/src/commands/daemon.ts

部署边界：只启动 Web 和数据库，用户可以管理频道和任务，但没有在线 Daemon 时，Codex / Claude 不会自动替你执行任务。

3. 一个常见用户故事

  1. 团队负责人在网页频道中发布需求。例如点名“后端工程师”分析一个接口故障。
  2. 服务层保存消息并创建任务。它验证频道权限、员工身份和执行环境绑定，然后将可自动执行的工作放入数据库队列。
  3. 匹配的 Daemon 领取任务。数据库事务保证多个 Daemon 中只有一个领取成功。
  4. Daemon 启动实际命令行 Agent。执行器路由选择 Codex 或 Claude 的启动适配器，在指定工作目录中运行。
  5. 需要敏感操作时暂停等待审批。用户在 Web 中批准或拒绝，系统保留这次决定和上下文。
  6. 执行结果回到统一记录。任务状态、过程事件、用量、允许公开的附件和最终回复被保存，并显示回原频道。

4. 先分清逻辑员工和实际进程

逻辑员工（Employee）

表示“谁应该负责这类工作”，包含身份、权限和所属工作区。它是一条长期业务记录，不等于正在运行的 Codex 或 Claude 进程。

执行环境绑定

说明这个逻辑员工应该由哪种本机或远程执行环境完成任务。没有绑定时，任务可以进入协作看板，但不能自动执行。

5. 创建任务时，系统先做业务校验

  1. 确认频道存在且调用者有权限。任务不能从一个无权访问的工作区或频道进入。
  2. 确认负责的逻辑员工存在。系统需要知道任务属于谁，而不是先随便启动一个进程。
  3. 创建任务看板记录。这让 Human 即使没有自动执行器，也能看到和管理任务。
  4. 检查执行环境绑定。有绑定才调用 enqueueNativeTaskSync 放入自动执行队列。

源码入口：packages/services/src/tasks/tasks.ts → createTaskSync

重要边界：“任务已经创建”和“任务已经有程序执行”是两种状态。AgentSpace 不会因为看板上出现了任务，就假装执行器已经存在。

6. 数据库怎样保证任务只被领取一次

入队时，系统保存任务、目标执行环境和连续会话记录。后台的常驻执行服务（Daemon）反复查询等待中的任务。

查询与自己执行环境匹配的等待任务
在一次数据库事务中把任务改成“已领取”
如果另一个 Daemon 已先修改，当前 Daemon 领取失败
只有领取成功者可以启动实际 Agent 程序

这个动作叫事务领取（claim）。关键不在“先查询再执行”，而在“检查和修改必须处于同一次数据库事务”，否则两个 Daemon 都可能看到同一项任务。

源码入口：packages/db/src/task-queue.ts → enqueueNativeTaskSync / claim

7. Daemon 领取后怎样启动不同 Agent

Daemon 启动时探测机器上有哪些 Agent 命令可用，注册对应执行环境，持续报告在线状态，然后轮询任务。同一种执行环境一次只运行一项任务，不同执行环境可以并行。

领取任务后，Daemon 把统一请求交给执行器路由层（AgentRouter）。路由层选择Agent 启动适配器（Harness），把 Claude Code、Codex、OpenCode 等不同命令和输出格式整理成统一接口。

Daemon已领取任务
执行器路由选择适配器
Codex / Claude执行并产生事件
完成服务写回结果

源码入口：apps/cli/src/commands/daemon.ts → packages/daemon/src/agent-router/router.ts

8. 频道消息怎样触发多个 Agent

普通频道消息只保存为协作记录。只有消息里明确点名了当前频道中的有效 Agent，服务层才创建工作。这样可以避免任意文本意外触发执行。

一条消息可以并行点名多个 Agent，也可以声明顺序交接。Agent 回复还可以继续点名下一个 Agent，但系统会记录根消息和传递深度，防止无边界地递归触发。

源码入口：packages/services/src/messages/messages.ts

9. 完成不是只写一个“成功”状态

执行结束后，系统会保存队列结果、模型用量、任务看板状态、连续会话、工作目录、过程事件和允许的附件，再向频道发送最终回复。附件必须经过输出清单、类型和大小限制，不能由 Agent 任意暴露文件。

如果命令行 Agent 失败，任务记录、执行次数、诊断信息和连续会话仍然存在，可用于重试、更换执行环境或重新开始。这就是 AgentSpace 把可靠性放在“任务记录”上的含义。

10. 运维怎样端到端排查

按链路检查：Web 能否连接数据库 → 员工是否绑定执行环境 → daemon status 是否在线 → 目标机器上对应 Agent CLI 和凭据是否可用 → 任务处于等待、已领取还是失败 → 执行事件和输出清单是否完整。不要只看到网页里有任务，就断定 Agent 已经开始执行。
