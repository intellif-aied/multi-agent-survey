学完实现之后
再比较四种设计

现在不再按仓库讲源码，而是用同一组问题比较：长期保存什么、何时启动进程、怎样通信、如何限制并发，以及失败后从哪里恢复。

比较原则：这里比较的是当前本地源码中的主要设计边界，不是性能排名或项目成熟度排名。需要快速查结论时，可打开四框架速查表。

1. 最根本的区别：长期保存什么

项目长期保存的核心对象任务结束后仍留下什么
AgentTeamsWorker 身份、配置和希望的容器状态聊天身份、Worker 状态、工作区文件；容器默认继续在线或进入休眠
AgentSpace任务、逻辑员工、执行环境绑定和连续会话任务结果、执行记录、消息、附件；命令行 Agent 进程不必保留
houmao可恢复的单 Agent 运行会话隔离工具配置、运行清单、登记信息、Gateway 队列和邮箱
omnigent父子 Session 树会话历史、父子关系、事件、产物和执行主机绑定

2. 四种进程生命周期

项目通常提前运行什么任务到来后做什么主要取舍
AgentTeams持续检查程序和默认在线的 Worker 容器消息直接进入 Agent；休眠时先唤醒响应快，空闲容器成本较高
AgentSpace业务服务和领取任务的 Daemon领取任务，再启动 Codex/Claude 等执行器资源贴近任务，首次启动路径更长
houmao已显式启动的 Agent 会话和稳定 tmux 窗口Gateway 或邮箱向现有 Agent 投递；无界面模式可每轮启动进程会话连续、人工可接管，需要维护每个 Agent 的状态
omnigentServer、Runner 和根 Session第一次委派时创建 Child Session 和 Harness子 Agent 按需扩展，首次子任务有创建成本

综合检索 ①

哪个系统最明确地把“逻辑员工”和“执行这个任务的进程”分开？

3. “谁把工作交给谁”也不同

项目做出委派决定者系统保证什么
AgentTeamsManager 或 Team Leader 根据提示词、技能和聊天室上下文选择 WorkerWorker 身份存在、容器达到希望状态、消息通道可用
AgentSpace频道点名、任务负责人和执行环境绑定共同确定目标任务只被一个 Daemon 领取，并由正确执行器启动
houmao操作者、上层 Agent 或显式流程选择某个已登记 Agent找到正确运行会话，并按单 Agent 准入规则投递
omnigent父 Harness 根据自身提示词调用某个逻辑子 Agent权限检查、Child Session 创建或复用、结果回到父会话

四个系统都没有把“如何拆业务任务”完全硬编码在基础设施里。基础设施主要保证身份、执行、路由和恢复；具体为什么选择某个 Agent，通常仍来自 Lead Agent、Human 或业务规则。

4. 通信方式反映了协作模型

项目主要通信方式适合的协作形态
AgentTeamsHuman、Manager、Worker 共享 Matrix 聊天房间所有参与者可观察、Human 可随时介入的团队协作
AgentSpace数据库工作区频道、消息和任务记录围绕业务任务看板和审计记录组织协作
houmao每个 Agent 的 Gateway 请求入口，加上异步邮箱长期独立 Agent 之间点对点发信或由外部流程控制
omnigent父会话委派工具、Child Session 事件和父会话 Inbox根 Agent 动态拆分并汇总临时子 Agent 工作

5. 并发限制放在不同位置

  • AgentTeams：每个 Worker 是独立执行循环，多个 Worker 天然并行。
  • AgentSpace：同一执行环境同时只运行一个任务，不同执行环境可以并行。
  • houmao：单 Agent Gateway 顺序处理请求，多个 Agent 各自运行。
  • omnigent：同一 Session 一次处理一轮输入，不同 Child Session 可以并行。

设计并发限制时，不应只问“最多开几个线程”，而应先问“哪些工作共享同一个上下文、工作目录或命令行进程，不能安全地同时修改”。

6. 故障恢复分别从哪里开始

故障首先检查的持久状态恢复动作
AgentTeams Worker 容器消失Worker 配置记录和对象存储工作区持续检查程序重建容器，Agent 恢复文件并重连 Matrix
AgentSpace 执行进程失败任务状态、执行次数、诊断、连续会话和工作目录重试、更换执行环境或转人工处理
houmao Agent 进程停止Session Manifest、tmux 状态和 Shared Registry校验原运行信息，恢复稳定窗口并重新登记
omnigent Runner 断开Server 中的 Session、父子关系、事件和 Runner 绑定重新绑定执行主机并启动 Harness

7. 可以组合，但要明确谁拥有最终状态

假设要构建一个长期在线的研究组织，可以这样借鉴，但这只是设计推演：

  1. 用 AgentTeams 的 Worker 生命周期维护长期研究员身份、聊天房间和休眠唤醒。
  2. 用 houmao 的运行清单和独立工具配置保存某个研究员的本机 Claude/Codex 会话。
  3. 用 omnigent 的 Child Session 模型创建一次课题中的临时搜索、编码和审稿子 Agent。
  4. 用 AgentSpace 的任务队列记录可靠领取、执行次数和业务任务完成状态。
组合时最大的风险：四层都可能保存“状态”。必须明确哪个系统拥有任务最终状态、哪个拥有 Agent 身份、哪个拥有工具会话、哪个只做缓存或投影，否则失败恢复时会互相覆盖。

综合检索 ②

组合四种设计时，最先需要明确什么？

最终练习：画出你自己的研究组织架构，只标四类状态：Agent 身份、业务任务、工具会话、协作消息。为每一类指定唯一的最终负责人，并说明其他系统保存的是副本、索引还是临时执行状态。
